# 02: 元数据补充与证据来源解耦

**What to build:** 元数据补充的核心部分可以接受提案以外的证据来源，为「识别确认后由服务端补充」铺路。核心部分包括：按字段校验期望值、写入字段、追加集合成员、留收据、写字段来源记录、撤销。这是纯预备重构，外部行为不变。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 补充拆成两段：「从已确认提案收集字段证据」和「把字段证据应用到系列并留收据」。后一段不再假设证据来自提案。
- [x] 字段来源记录、以及撤销时回收这些记录，都可以关联到提案以外的证据来源（例如一条识别结论）。撤销只回收本次操作写入的来源记录。
- [x] 以下功能的外部行为与收据格式不变：现有的补充、批量补充、提案裁决、撤销与清理。现有集成测试不改断言即通过。
- [x] ADR 0011 的事务内终态守卫保持不变。
- [x] 后端门禁通过。

## Comments

本票按规格「留给实施决定的工程细节」自己定下的取值：

- **持久化结构**：`series_metadata_provenance` 加可空列 `operation_id`，记写入该来源记录的补充操作（收据 ID）；`review_id` 仍只在证据来自提案时填。没有为识别结论另开列：识别表归 03，来源记录经操作收据追溯到证据来源，07 在收据里补识别引用即可，不必再动这张表。
- **撤销认领规则**：撤销只删 `operation_id` 等于原操作的记录；升级前写入、`operation_id` 为 NULL 的记录，由带裁决的原收据按其提案认领，与升级前语义一致。理由：存量记录没有写入者信息，只能沿用原判据。
- **应用层接缝**：第二段 `applyEvidence` 只认 `decision`（额外授权、写事务内终态守卫、收尾、写失败复位四个钩子）；来源记录由 decision 收尾时调 `recordProvenance` 写，普通提案补充仍不写来源记录、不消费字段（行为不变）。理由：07 的识别确认只需另实现一个 decision，守卫换成重读识别、收尾换成写来源记录并结案旧提案。
- **测试**：新增 `TestProductionLegacyAdjudicationUndoReclaimsOwnProvenance`，用 81a8807f 生产组装产出的静态库（`internal/bootstrap/testdata/enrichment-adjudication-legacy.*`）走启动升级、管理员 HTTP 撤销，验证存量记录只被自己的操作回收。非提案来源这条路径本票没有公开入口，由 07 的集成测试在公开接缝上覆盖。
